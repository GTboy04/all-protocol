# Modbus 场景二次开发与从站配置隔离设计

2026-11-16 · 状态：已按首版范围实现。操作见[场景扩展指南](modbus-scenario-extensions.md)，交付与验证见 [R21](requirements/R21-scenario-extensions.md)。

本文基于当前工作区代码，承接已有基础场景、Modbus TCP 从站独立启停及日志清空功能。文中的 API、数据结构和版本号描述首版设计契约。下文保留设计时的契约与模块建议，实际交付情况以 R21 记录为准。

## 1. 可行性与目标

可以实现。现有程序已经具备类型化点位、运行值读写接口、单调时钟场景引擎和服务端会话，不需要重写 Modbus 协议栈。

本次增加两项能力：

1. **条件联动与代码扩展**：某点位进入指定值时，立即修改其他点位，并在触发后的指定时刻依次赋值。用户能用 Python 编写扩展定义，随方案保存、复制和复用。
2. **按从站隔离配置**：选中 Unit ID 后，只显示该从站的点位、基础场景和扩展定义；所有编辑操作明确显示当前从站 ID。

保留已经设定的固定值、递增、心跳、斜坡、正弦和时间轴规则。新增联动配置独立保存，不把旧规则转换成脚本，也不覆盖旧规则参数。

## 2. 用户示例与验收结果

以同一模拟服务下的 Unit 7 为例，偏移全部为 0 基：

| 点位 | 类型 | 用途 |
|---|---|---|
| Unit 7 / HR / 0 | UInt16 | 启动指令，进入值 10 时触发 |
| Unit 7 / HR / 10 | UInt16 | 过程状态，依次为 1、2、3、0 |
| Unit 7 / Coil / 0 | Bool | 完成标志 |

一次动作序列如下：

| 相对触发时间 | 动作 |
|---|---|
| 0 秒 | HR / 10 = 1，Coil / 0 = 0 |
| 2 秒 | HR / 10 = 2 |
| 5 秒 | HR / 10 = 3 |
| 8 秒 | HR / 10 = 0，Coil / 0 = 1 |

这里的 5 秒表示“触发后第 5 秒”，与上一动作间隔为 3 秒。界面、SDK 和日志均使用这一口径。

Unit 8 配置相同地址时，不因 Unit 7 的条件满足而改变。HR / 0 持续为 10 时只触发一次；先变为其他值，再进入 10，才能再次触发。原有基础场景配置仍然存在，扩展停用后可恢复。

## 3. 当前实现与改动依据

| 当前模块 | 已有能力 | 本次缺口 |
|---|---|---|
| `application/simulation.py` | 单点规则、时间轴、约 20 ms tick、暂停/重置、写入接管 | 没有跨点条件、触发实例或扩展写入所有权 |
| `application/server_session.py` | 管理模拟服务生命周期、场景任务和运行值接口 | 只在存在基础规则时创建场景引擎；扩展单独存在时也要能运行 |
| `adapters/modbus_tcp/server_model.py` | 点位标识为 `(unit_id, area, offset)`；每点保存一条基础规则 | 缺少从站级扩展定义 |
| `adapters/modbus_tcp/server_adapter.py` | 转发 `ValuesChanged` 和成功写入的 `WriteSpan` | 缺少完整的前后值、写入来源和一次提交编号 |
| `ui/simulation_dialog.py` | 列出 `plan.simulation_points()` 的全部点位 | 会混合展示所有从站；选中项依赖列表行号 |
| `ui/modbus_server_pane.py` | 主点位表按当前从站展示；基础规则按完整目标写回 | 场景弹窗需要接收当前 Unit ID，并按目标标识保存选择 |
| `storage.py`、`database.py`、`project.py` | 本地 SQLite、项目 SQLite/JSON、基础规则序列化 | 新的从站扩展字段必须贯穿所有存储路径 |

点位底层身份已经包含 Unit ID。本次“隔离”主要补齐界面过滤、扩展引用范围和运行态归属，不能只把下拉框标签加上 Unit ID 就算完成。

相关背景：[R7 基础场景](requirements/R7-simulation.md)、[多模拟设备](multi-device-simulation.md)。[R15 联调用例](requirements/R15-test-workflows.md)面向客户端测试流程，本设计面向模拟服务内部点位联动，可独立实施。

## 4. 首版范围与执行方式

首版交付 Modbus TCP，支持同一模拟服务、同一 Unit ID 内的点位联动。结构保留协议扩展接口；Modbus RTU、S7、OPC UA 接入另行验收。

提供两个编辑入口，使用同一个运行引擎：

- **条件联动表单**：选择源点位、比较条件和目标点位，填写按触发时刻计时的动作表。
- **Python 扩展编辑器**：用户通过 SDK 编写条件和动作定义，检查后生成与表单相同的结构化执行计划。

首版 Python 在“检查代码”时执行，用于生成执行计划。运行期间由程序识别点位变化并执行计划；不在协议 I/O 线程中执行用户函数。此方式已经覆盖本次“值触发 → 修改另一点 → 延时依次赋值”的代码二开需求，也允许用 Python 的函数、循环和参数生成多条规则。

任意运行期 Python 回调、动态网络访问、用户自定义实时计算和第三方依赖安装不纳入首版。后续若需要，可增加版本化的独立进程回调接口，沿用本设计的提交与写入仲裁接口。

首版不跨从站、不跨模拟服务、不写真实设备，不支持运行中替换配置。保存和编辑在停止监听时进行，运行中只进行启用、停用、暂停、重置和释放控制等已定义操作。

## 5. Python SDK 草案

SDK 的点位引用始终相对于当前扩展所属从站，编辑器顶部固定显示实际 Unit ID 和监听端点。下面的代码在 Unit 7 页面执行检查时，全部引用都会绑定到 Unit 7。

```python
from all_protocol.scenario_sdk import Scene, Step


def build(scene: Scene) -> None:
    command = scene.point("HR", 0)
    state = scene.point("HR", 10)
    done = scene.point("Coil", 0)

    scene.when_equal(
        id="startup_sequence",
        source=command,
        value=10,
        edge="enter",
        busy="ignore",
        completion="hold",
    ).sequence([
        Step(at_ms=0, values={state: 1, done: 0}),
        Step(at_ms=2000, values={state: 2}),
        Step(at_ms=5000, values={state: 3}),
        Step(at_ms=8000, values={state: 0, done: 1}),
    ])
```

API 约定：

- `scene.point(area, offset)` 只接受当前从站中已配置的逻辑点位起始地址，不接受名称作为身份，不允许传入其他 Unit ID。
- `when_equal` 首版支持整数/Bool 精确比较；浮点比较必须显式提供 `abs_tol` 和 `rel_tol`，禁止 NaN、Infinity。通用条件模型可覆盖 `eq/ne/gt/ge/lt/le`。
- `Step.values` 在同一时刻作为一次写入批次，整批预校验后提交。
- `at_ms` 为非负整数、按非降序排列；同一时刻的动作合并，重叠目标或冲突值拒绝保存。正延时最低 20 ms，0 表示立即调度。
- SDK 不提供 `sleep`、直接访问适配器或直接读写内存的方法。时间等待由引擎维护。
- 一份代码可生成多条规则，规则 ID 在该扩展内唯一；所有读写引用均进入检查结果的目标清单。
- 检查成功后显示“Unit ID、触发条件、动作时刻、实际写入目标和值”，与源码一起保存。

SDK 版本首版为 `1`。示例接口现已实现，可在 Python 扩展编辑器检查与运行。

## 6. 模型与身份

建议在 `Station` 末尾增加 `extensions: tuple[ScenarioExtension, ...] = ()`，保留现有 `points` 和 `ServerPoint.simulation` 字段。

| 模型 | 主要字段 |
|---|---|
| `ScenarioExtension` | UUID、名称、编辑方式、源码、SDK 版本、内容摘要、生成的规则清单、配置启用标记 |
| `ConditionalRule` | 规则 ID、源目标、操作符、比较值/容差、边沿、触发来源、忙时策略、完成策略、步骤 |
| `SequenceStep` | `at_ms`、目标赋值列表 |
| `BoundPointRef` | `unit_id`、`area`、`offset`、类型/跨度签名 |
| `PointCommit` | 提交序号、来源、完整逻辑点位的前后值、受影响地址范围 |
| `ScenarioRun` | 运行 ID、扩展/规则 ID、会话代次、所属从站代次、开始时刻、下一步骤、状态、持有目标 |
| `WriteOwner` | 完整点位范围、所有者、取得时间、释放原因 |

项目运行时身份使用 `(simulator_id, session_generation, unit_id, area, offset)`；本地模式由当前服务实例生成对应的运行标识。协议适配器内部继续使用现有 `ModbusServerTarget`，不把项目 ID 硬塞进协议地址。

名称只用于显示。运行前冻结点位类型、跨度、字序与引用；目标删除、地址改变或类型改变后必须重新检查扩展，禁止静默按旧地址执行。

新增 `Station` 字段后，编辑从站应使用 `replace(original, ...)` 保留扩展，不能继续通过只传 `unit_id/name/points` 的构造方式丢弃新字段。

## 7. 触发规则

### 7.1 边沿与首次运行

默认 `edge="enter"`：条件从“不成立”变为“成立”时触发。重复写入相同值不会产生新触发。条件恢复不成立后重新布防。

启动扩展时先读取当前值建立基线，默认不因启动时已经满足条件而执行。可提供显式的“首次启动满足即触发”选项，默认关闭。暂停后继续、从站重新启用及手动恢复扩展也重新建立基线，避免把暂停期间的状态误当成新边沿。

### 7.2 变化来源

默认监听外部客户端成功写入、本机当前值修改和基础场景提交。扩展自身写入、场景重置不触发新的扩展，防止 A 写 B、B 再写 A 的自动循环。

成功写入即使与旧值相同，仍保留原有手动接管语义；只有实际值变化才参与条件边沿判断。

触发源必须处于已启动从站中，并且能够读取有效运行值。未启动从站不能用配置初始值替代当前值参与条件判断。

### 7.3 重复触发

首版固定 `busy="ignore"`：同一规则执行期间的新触发不叠加、不排队、不自动重启。记录“执行中，忽略本次触发”。条件随后离开并重新进入时才有下一次执行机会。

条件在执行中变为不成立，默认继续既定序列；如业务要求“条件失效即取消”，通过单独的配置项开启。取消保留已经写入的值，不宣称回滚。

### 7.4 提交与多字点位

必须依据提交事件判断变化，不能只每 20 ms 轮询当前值，否则可能漏掉两次 tick 之间的短脉冲。

Modbus 多寄存器写入在整次请求提交后，重建受影响的完整逻辑点位再比较。对 UInt32 的一个寄存器进行部分写入，也使用提交前后的完整解码值判断，禁止以中间半字值触发。

一笔多点写入中的条件统一看到本次提交完成后的快照，不能读取混合的新旧值。无效地址、类型越界或协议拒绝的请求不触发。

## 8. 调度与延时语义

每个模拟服务使用一个 `ScenarioRuntime`，共享现有服务端 I/O 事件循环和单调时钟。扩展不创建独立睡眠线程，也不为每一步堆积一个长期休眠任务。

执行顺序：提交运行值 → 发布变化 → 按提交序号处理触发 → 获取输出控制权 → 执行到期动作 → 发布结果。回调只入队，不在写值回调中递归执行另一条规则。

- 使用小顶堆维护 `(due_time, run_id, step_index)`，按到期时间和稳定顺序执行。
- 0 ms 动作在触发提交后的下一次调度执行，不等待固定 20 ms 周期，也不修改原 Modbus 写入请求的应答含义。
- 延时按场景的有效运行时间计算；暂停冻结剩余时间，继续后接着计时。
- 普通短延迟导致多个步骤同时到期时，按原顺序补执行，不直接跳到最终值；但这不保证外部轮询客户端能观察到每个中间值。
- 建议首版设置 `max_lateness_ms=1000`。超过允许延迟则将该执行标记为时序异常并取消后续步骤，避免长时间卡顿后集中补写。该值作为拟定默认值，需要基准测试确认。
- 这是桌面联调时序，不承诺硬实时。记录计划时刻、实际时刻和偏差；验收关注不提前执行、顺序正确和实际误差可观察。
- 重置、服务停止或规则取消后，使用运行代次和取消标记使旧队列项失效，不能靠单纯清空 UI 状态代替任务取消。

建议初始限制为每从站 100 条规则、每规则 1000 步、每模拟服务 256 个同时执行实例，作为可调整的产品限制。达到上限时明确拒绝触发；事件队列溢出时停用相关扩展并记录缺失，不能继续声称时序完整。

## 9. 与已有基础场景共存

配置保留与运行写入冲突是两件事。所有运行写入必须经过统一 `WriteArbiter`，按完整地址范围仲裁。

| 来源 | 行为 |
|---|---|
| 本机手动修改、外部客户端成功写入 | 保持原有接管优先级；写到某次扩展的输出范围时，取消该执行并释放它的全部输出控制权 |
| 条件联动/代码扩展 | 触发时一次获取全部输出点的控制权；期间基础场景暂停对这些点写值 |
| 基础场景 | 对未被接管或占用的点继续运行，原规则参数不变 |

运行前检查所有已启用扩展的输出范围。首版拒绝不同规则声明重叠写入范围，即使用户认为它们不会同时触发，也不采用“最后写入者获胜”。UInt32 与内部单字地址重叠同样算冲突。

开始一次序列时，任何输出点已被手动接管，或者相关从站未启动，则整次启动失败，不先改一部分点再等待。手动写入的点按原有机制保持接管；被取消执行的其他输出点释放后可恢复基础场景。

完成策略：

- 默认 `completion="hold"`：执行结束后保留最终值和扩展控制权，界面显示“已完成，保持输出”。同一规则下一次触发可复用自己的控制权。
- 可选 `completion="release"`：完成后释放，基础场景按当前服务场景时间恢复；无基础规则的点保持最后值。
- 提供“释放扩展控制 / 恢复基础场景”，只释放当前扩展持有的点，不清除其他来源的手动接管。

恢复基础场景时必须使该点的 `_last` 缓存失效；时间轴恢复当前设定值，不重放被占用期间的全部历史动作。否则可能出现基础规则认为已经写过、界面却仍保持扩展值的问题。

## 10. 生命周期与从站独立启停

| 操作 | 基础场景 | 新增扩展 |
|---|---|---|
| 启动服务 | 保持现有就绪状态，手动启动场景 | 校验并就绪，不自动触发 |
| 启动场景 | 按现有规则运行 | 启用已通过检查的联动监听，建立基线 |
| 暂停场景 | 冻结时钟、保持值 | 暂停条件监听和动作计时；暂停期间不积压触发 |
| 继续场景 | 继续既有时钟 | 重建条件基线，已有序列按剩余时间继续 |
| 重置场景 | 保持现有初始值恢复语义 | 取消实例、释放所有权；恢复扩展输出目标的方案初始值；不触发联动 |
| 停用某个从站 | 沿用当前暂停写值、重新启用后按服务时间继续的行为 | 立即取消该站全部扩展实例及保持控制权；不在站重启后重放旧动作 |
| 再次启用从站 | 保留当前值并恢复既有基础规则行为 | 已启用规则重新布防，等待新的有效边沿 |
| 停止服务/关闭项目 | 等待场景任务结束 | 取消所有队列项、编译进程和实例，旧代次不能继续写值 |

从站停用时，扩展取消但保留已写入的运行值，避免改变现有单站停用保值约定。对于已停用从站，重置记录“待恢复初始值”，下一次启用时先恢复后布防，不能调用目前拒绝离线点位写入的接口硬写。

扩展单独存在、没有任何基础规则时，也必须创建运行引擎，并允许启动场景。需要修改当前 `configured_only=True` 为空即不创建 `Simulation` 的判断。

单个扩展报错时停止该扩展、取消剩余动作并释放输出控制权，其他从站、基础规则和 TCP 监听继续运行。之前已经提交的值不会自动回滚。

## 11. 场景界面按 Unit ID 隔离

打开「场景模拟」时，默认使用主界面当前选中的从站。窗口顶部显示：

```text
模拟服务：温控网关  127.0.0.1:1502
当前从站：Unit 7 · 温控器    状态：运行中
配置范围：仅 Unit 7
[基础场景] [条件联动] [Python 扩展]
```

交互约定：

1. 从站选择器可在已配置从站间切换；没有从站时展示空状态，禁用规则编辑，不默认选择 Unit 1。
2. 点位下拉框只列所选从站，标签明确包含 `Unit 7 / HR / 10 / 过程状态`。无扩展规则时也可以选择该站所有已配置点位。
3. 下拉框通过 `itemData` 保存完整目标；过滤和排序后按目标恢复选择，不能用旧列表行号定位或写回。
4. 条件源和动作目标选择器受同一从站过滤。代码检查结果中的实际目标也逐项展示 Unit ID。
5. 切换从站时刷新规则、当前值、接管状态、错误和执行列表。未应用的编辑先保留当前编辑上下文或提示处理，不能把 Unit 7 的草稿提交到 Unit 8。
6. 弹窗关闭时保留最后查看的从站选择；主界面原从站选择和弹窗选择的同步需通过明确的选站接口，不直接访问任意控件行号。
7. 现有启动/暂停/重置按钮继续控制整个模拟服务的场景，按钮旁明确标注“整个模拟服务”。本次只改变配置展示范围，不暗中把全局控制变为单站控制。
8. 扩展列表的启用、停用和释放输出操作只作用于所选从站/扩展，不能据此启停整个服务。
9. 配置编辑仅在停止监听时启用。运行时查看冻结的配置和状态；“已配置但未启动从站”与“扩展异常”分开显示。

其他协议继续显示原有点位选择逻辑；通过协议提供的分组接口接入，不能在通用 `SimulationDialog` 中直接假定存在 Modbus `_station`。

## 12. 模块划分与接入点

建议新增以下模块，最终文件名可在实现时微调：

| 模块 | 职责 |
|---|---|
| `application/scenario_model.py` | 条件、步骤、扩展、执行实例及校验错误模型 |
| `application/scenario_runtime.py` | 提交事件消费、边沿判断、动作堆、暂停与取消 |
| `application/write_arbiter.py` | 写入来源、范围占用、接管及恢复 |
| `scenario_sdk.py` | 稳定的 Python 定义接口，不导入 Qt 或协议服务端 |
| `scenario_worker.py` | 在独立进程执行 `build(scene)`，输出受限 JSON 执行计划 |
| `ui/scenario_extension_editor.py` | 条件表单、Python 编辑、错误行和实际目标预览 |

现有模块的关键改动：

- `ServerSession` 统一管理基础场景和扩展，持有 `WriteOrigin` 上下文。现有 `_simulating_write` 只能区分模拟/非模拟，不能把扩展写入误认成外部手动接管。
- `ServerCallbacks` 增加可选的提交回调，保留现有 `changed` / `written` 兼容入口；接入时避免同一写入被接管两次。
- `RuntimeValues` 提交前收集旧值，提交后发出带序号和来源的变更。失败写入不能发成功提交事件。
- 适配器提供原子批量运行值写入能力：同一时间步骤先编码和验证全部目标，再一次更新数据、发布提交。不能用一组可能中途失败的 `write_current` 循环冒充原子写入。
- 基础场景的采样仍由现有 `Simulation` 完成，通过仲裁器决定能否写入，保持原有波形编译结果和时钟语义。
- 从站启停要直接通知扩展运行时取消/布防，不能只依赖下一次 tick 读取 `active` 集合。

所有写入提交仍由服务端事件循环处理。编译进程只产生执行计划，不能持有活动适配器引用。

## 13. 扩展检查、进程边界与打包

源码编辑与保存不自动执行。用户点击“检查代码”时，在独立进程运行约定入口 `build(scene)`，通过标准 JSON 返回执行计划。主进程再次校验字段、引用范围、值类型、步骤数量、总时长和输出冲突，不能信任工作进程返回的结果。

建议检查超时为 3 秒、源码上限为 256 KiB、单份执行计划上限为 1 MiB；这些是拟定限制。超时、语法错误、入口缺失或返回非法内容时，显示行号和原因，保留原已应用配置，不改变基础场景。

Python 独立进程用于限制卡顿和隔离崩溃，**不构成运行不可信代码的安全沙箱**。首版仅支持用户信任的扩展；项目导入或源码摘要变化后须重新检查并显式启用。运行许可按内容摘要保存在本机，不随项目传递。不以禁用几个 import 或 builtin 宣称安全隔离。

执行计划与源码摘要、SDK 版本和点位签名绑定。摘要不一致时禁用扩展并提示重新检查。表单规则修改时重新生成计划；Python 代码保持只由代码编辑，避免表单反写丢失注释和函数。

开发态可使用模块入口启动 worker；Windows 打包态为程序自身的 `--scene-worker` 入口，不能假定用户安装了系统 Python。启动 worker 不显示控制台窗口。停止检查或退出程序时终止并回收进程，worker 入口不得创建主窗口或监听服务。

## 14. 保存、兼容、复制与导入导出

### 14.1 版本提案

- Modbus TCP 方案存在扩展时使用 `schema_version=5`，读取时兼容旧 v1–v4；无扩展的方案沿用当前版本选择逻辑。
- 项目包含扩展时使用外层 `schema_version=9`，兼容读取旧 v1–v8。旧程序应因不支持的新版本而明确拒绝，不能加载后静默丢失扩展。
- SQLite 物理表结构首版可不变：用 metadata 中的 `scenario_extensions:modbus-tcp` 保存按 Unit ID 分组的扩展对象。`write_plan` 与 `read_plan` 必须成对实现，不能只改 JSON 编解码器。
- 该 metadata 与点位、基础规则在同一事务写入；保存无扩展方案时清除旧扩展 metadata，防止旧定义重新出现。
- 项目旧式 `servers` 路径和多实例 `simulators` 路径都要往返保存。无需新物理表时不提高 SQLite `user_version`；若实现改为新表，必须另行设计数据库迁移并补验收。

持久化源码、SDK 版本、执行计划和配置启用意图。不保存当前值、开始时刻、剩余延时、执行实例、所有权和本机信任状态。重新打开项目不会自动启动服务或重放序列。

### 14.2 复用与引用维护

- 复制从站：保留基础规则，复制扩展并生成新的扩展 UUID；点位引用绑定目标从站，不能继续写源站。复制后重新检查，运行状态不复制。
- 修改 Unit ID：按结构化引用统一重绑定并使检查摘要失效；不搜索替换源码中的数字。
- 删除被引用点位或改变类型：在停止状态阻止应用修改并列出受影响扩展；用户先修改或移除引用，不能静默删除扩展。
- 改名不改变目标身份；整站删除按现有确认逻辑列明同时删除的扩展数量。
- 现有 JSON/CSV 点位导入导出继续只处理点位及其基础规则，不暗中夹带可执行源码。扩展通过独立、带版本的 JSON 包导入导出，或随完整方案/项目复制。
- 扩展包包含源码、规则及点位依赖，导入时绑定用户选中的 Unit ID，检查地址和类型；失败不部分修改配置。

## 15. 日志与运行状态

界面展示扩展名称、Unit ID、规则 ID、执行 ID、当前步骤、剩余时间、最终输出保持状态和最近错误。

新增类型化 `ScenarioEvent`，记录触发/忽略/开始/步骤提交/完成/取消/释放/失败；包含计划及实际执行时刻、源点位前后值、写入目标和值、来源提交序号、会话与从站代次。日志使用墙上时间显示、单调时钟计算延时，不依赖修改系统时间调度。

场景内部赋值不是网络请求：不能伪造 RX/TX 或把一次内部动作计作 Modbus 请求成功。适配现有 `_ServerJournal`、后台批量写入、诊断与报告的日志类型白名单，明确区分请求统计和场景事件。

复用日志容量与后台队列上限；高频变化仅记录已执行步骤和关键生命周期，不逐 tick 刷屏。清空日志遵守当前设备/服务端点范围，仅清日志，不取消正在运行的扩展；清空后新步骤继续记录，报告标明记录起点或缺失。

## 16. 开发拆分与交付顺序

| 阶段 | 内容 | 可独立验收的结果 |
|---|---|---|
| A | 场景窗口分组接口、Unit ID 过滤、完整目标选择 | 两站同址点位配置不串站，旧场景原样保存 |
| B | 条件/步骤模型、提交事件、虚拟时钟调度、写入仲裁 | 用结构化配置跑通触发和 0/2/5/8 秒序列 |
| C | 与原有基础规则、接管、暂停/重置、从站启停联动 | 最终值保持与基础场景恢复可预测，旧任务不复活 |
| D | Python SDK、编译 worker、编辑器、检查预览 | 用户修改示例源码即可生成和运行同一序列 |
| E | 方案/项目保存、复制、扩展包、事件日志和报告 | 重开后定义完整、运行不自动恢复、日志可追溯 |
| F | 真实 TCP 回归、Windows 构建与窗口操作验收 | 打包程序无需系统 Python 即可检查并运行扩展 |

A 可以先交付；完整的“代码二开”功能以 A–F 全部完成为验收边界，不能仅交付一个 Python 文本框或条件表单就宣称完成。

## 17. 验收清单

### 功能与隔离

- Unit 7 / HR / 0 从 0 进入 10，目标按 0、2、5、8 秒依次变化；同一站多个不同数据区目标正确。
- Unit 8 同址点位和不同模拟服务的 Unit 7 同址点位均不受影响。
- 场景窗口只列当前从站，编辑、移除、复制、保存、重开后仍绑定正确 Unit ID；过滤后不能因旧行号操作其他站。
- 原有六类基础规则的配置与行为回归通过；仅有扩展时也能运行场景。

### 触发与仲裁

- 同值重复写、启动时已满足、条件离开后重入、忙时再次触发、浮点容差均符合约定。
- 20 ms 内出现的真实提交边沿不会因 tick 采样遗漏；多字点位部分写入按完整值判断。
- 基础规则触发扩展；扩展自身写入和重置不形成循环。
- 输出范围冲突在运行前报错；手动/客户端写入取消相关执行并保留接管优先级。
- 默认完成后保持最终值；释放后基础规则按当前时刻恢复，不能被 `_last` 缓存漏写。

### 时间与生命周期

- 虚拟时钟验证不提前执行、绝对时刻、暂停剩余时间、取消、重置及过期动作处理。
- 停用 Unit 7 后，没有 Unit 7 的延时写入；Unit 8 和 TCP 监听继续工作。
- 再启用、停止重启、关闭项目后，旧会话/从站代次的动作不能写入。
- 同时间步骤多目标先完整校验；任一值非法时整步不提交，不出现部分更新。

### 代码、存储与交付

- 示例 Python 能检查、显示实际目标、保存、重开和执行；源代码注释与顺序保留。
- 语法错误、无限循环导致的检查超时、非法引用、越界值、超大执行计划均保留原方案并给出明确错误。
- 新旧本地方案、JSON 项目、SQLite 项目及多实例项目兼容；无扩展保存不残留 metadata。
- 复制从站、修改 Unit ID、删除依赖点位符合引用规则；仅导入点位不执行代码。
- 清空日志不打断扩展；后续事件正常记录，报告不把内部动作计作网络请求。
- Windows 打包产物检查代码时无额外控制台，退出后无残留 worker 或定时任务。

文档中的首版默认值已给出明确建议。实施前需通过运行基准确认资源上限与延迟阈值，其他默认语义可直接据此开发。
